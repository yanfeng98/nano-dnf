# 地图窗口与清房开门复核

状态：业主已选择「全部按推荐」，实现及自动验证已通过，等待实玩验收。原有工作区修改保留。

2026-10-28 实玩反馈：「右上角的地图好像不对，而且怪物都打完了，门没有开」。

## 已核实

- 修复前 `main.js` 默认 `mapMode="radar"`；雷达把地图图块放大两倍后裁进半径 45px 的圆盘，直径容纳约 2.5 格的范围。方形整图已存在，Tab 可切换。
- 修复前 `render.js/drawGate` 在 `exitMode` 已为 open 时仍可能绘制 `shape.door`：普通关卡必定走这个分支；深处只有人物走到门口才改画蓝符文。因此「可通行」与「仍有拦门板」可以同时出现，视觉确有误导。
- 修复前 `core.js/resolveRoom` 用存活敌人和 `pendingWave` 判断清房，却未统计后续 `pendingWaves`。这会在空批次边界提前开门，已用专门回归修正；它不是不开门的同一根因。
- 用户截图中可见多个怪物外形，仅凭静帧不能判定它们是存活敌人还是死亡表现；不据此否定用户的实玩反馈。

## 已确认决定

1. 将方形整图设为默认，保留 Tab 切换圆形雷达及既有迷雾/领主标记规则。
2. 在清房后立即撤掉拦门板，使画面与可通行判定一致；所有批次结束之前仍保持锁门。

补充查证：入口在 exitMode 中标为 open，却被 resolveRoom 的未清房提前返回拦住，现已修复。未清房回退要求主动走到入口外沿，避免战斗误触。

对两个关卡的 150 间房间逐批调用 damageEnemy 并推进结算，均正常清房；未复现尸体阻塞清房。后续批次遗漏另有空批次回归覆盖。决定见 ADR-0067。术语沿用 `CONTEXT.md` 的地图窗口、雷达形态和房间门口。

## 验证

- `npm test`：293/293，涵盖远离门口时不绘制开门门板、未清房主动回退、空批次后仍有敌人时不提前清房，以及既有全关卡通关。
- `npm run test:browser`：键盘全关通关、深处冒烟、城镇冒烟全部通过；新增默认方图、Tab 往返切换、真实键盘穿过清房门及从未清房入口回退。
- 已检查 `tests/browser/artifacts/map-door-open.png` 的实际画面。试玩服务在 8080 返回 200；业主实玩尚待确认。
