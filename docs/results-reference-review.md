## 原件发现及边界

现代包与70包的`sprite_interface_newresult.NPK`含经典`result.img`：

- frame0：455×190的战绩底板，含韩文/英文原标签，与录像本地化底板布局并不完全一致。
- frame1：420×420蓝色魔法阵；frame2：227×227较亮魔法阵。
- frame3/4/5/6/7/8/9/10/11：SSS/SS/S/A/B/C/D/E/F圆形金色评级；frame5为141×142。
- frame12为英文Results，不是录像中的中文金色“战绩”，不能直接声称已找到中文标题原件。
- 其余帧含颜色数字、金色进度条、经验分解条及光效。

V1 339s圆形S按1.125缩放，与原件frame5匹配约0.891，位置约(129,320)、159×160。
录像战绩外框约(104,68)..(616,282)，对应455×190乘1.125；但原件内部英文/韩文标签及
第一行边框跨度仍不同，不能只把整张图贴上就称逐像素一致。
大魔法阵可能旋转并使用叠加混合，初次未考虑旋转的匹配较弱，须继续量。

70包`newresult/reward.img`与现代包`interface2/reward_ver2.0/reward_ver2.img`均有对应的旧式
宝箱、卡背与金色牌面。当前UI.rewardChest实际上取frame36金色卡面，变量名及旧注释容易误导，
**不能只凭名字便断言四张牌画成了红宝箱**。
frame35奖励列表/魔法阵板为527×270；当前drawRewardPage把它拉到960×492，布局需新量。
frame53..55为红色大宝箱，frame56/57魔法阵，frame58白青光，frame60玩家名条等。

扫描现代/70版542个interface包的条目，未找到额外的同路径中文result.img或reward.img；
“简体/翻牌界面补丁”路径仍需按实际帧内容检验，不能凭包名认定对应录像。
客户端Fonts/Gasinamu.ttf是旧式3/5编码的韩文字体，不能当Unicode中文字体直接用；
msjh.ttf有28958个Unicode字符且覆盖结算中文字，但尚未证明其与录像字形一致。

## 需优先验证的评分文字

render.js约9029行把录像“SS”解释成“55”，目前画rating.score数字。
旧ADR0041曾记录4→5次被击时从SS降到S，与该解释冲突。`newresult/result2_mainhud.img`
恰含SSS/SS/S等白色等级字形，应对原录像裁片进行模板比较，排除数字5的误读后再改。

两片结算都显示“总分 /140”：V1 85/140、操作60/85%、技巧40/57%、被击数-15；
V2可见77/140且被击数-23。可能与每项70分及每击-1有关，但仍需独立验证，

## 第二十四批：固定本局结算评分

本批只修复数据稳定性，不将当前评分公式、界面或时序认定为符合录像。

确定性复现：创建一局，将时间置于360秒、被击数3、攻击10次命中8次，进入胜利或失败；
随后只推进600帧。旧实现的评分82降到81，说明展示时间被计入战斗时间。
新实现于胜负首次确定时保存冻结的`resultRating`，`ratingOf`后续返回该快照。
失败可能发生于同一帧后半段，因此帧尾也记录首次结束状态，避免下一帧才取统计。
新局仍使用实时评分，未改变当前公式与奖励数值。

回归分别覆盖胜利与失败：等待不变、后续统计和等级变化不改写已结束结果、新局独立。
命令：`node --test --test-name-pattern='keeps the result rating stable' tests/core.test.js`。
