# 一间房摆到录像那个密度：六十件布景、一群怪、远景钉在屏幕上

**Status**: accepted（2026-10-13）。业主在 grill 上答 **「按照推荐做」**：
Q20（**照录像摆满**）、Q21（**怪聚成坨**）、Q22（**远景钉在屏幕上**）。

量自业主的整场录像 `dnf-dungeon-videos/00001-幽暗密林.mp4`（1920×1080，游戏画面居中
1440×1080）。录像像素 → 世界像素过 `Core.VIDEO_PX`（84/265）。

## 决定

**一、一间房 50–90 件布景，缺的按种子撒。**

量出来的差距是**十倍**：

| | 录像（一间房） | 本作（改之前） |
| --- | --- | --- |
| 布景件数 | **50–90 件** | **4–8 件** |
| 走位带被装饰的比例 | **75–95%** | **不到 10%** |
| 一屏内（同时看得见） | 短草 8–16 丛、粉花 10–15 朵、高草 0–5 丛、石头 2–7、木桶/木料 1–3 | 每样**一件** |

**手写的那几件留着**（它们是这间房的地标：门口那两棵树、挡路的那块石头），
缺的那批由 `SCATTER` **按种子撒**：矮草丛 30、粉花 26、高草 8，一间房落在 **68–72 件**。

**撒的只用不挡人的那几档。** 立着的实心件仍然由人写 —— 怪不会绕路、会顶着它
原地推（`docs/adr/0032`），几十块撒出来的石头会把它们顶死。

**它走自己的一条随机流**（`layoutRandom`，和地牢洗牌同一个做法），不碰 `nextRandom` ——
那一条是敌人抖动与掉落共用的，动它整段演示都会变。种子按**格**（`state.cell`）错开，
所以同一间房落在不同格子上不长成同一副样子。

**二、一群怪是聚着的，不是一字排开。**

量出来：同时在场 2–4 只；**相邻两只见中位 0.70 身位**（59 世界像素）；
**整群展开中位 1.32 身位**（111）；而且**不围着人转** —— 有的在他身前、有的在他身后。
本作原来是 `x 620/790/880` 一字排开（跨 260），现在三只跨 **118**、两只跨 **58–60**，
体宽大的（牛头）按体宽让开。**Boss 房不动**：录像里 Boss 房是 Boss 单独一个、
小兵只在门口那一带。

**三、远景钉在屏幕上，不跟着房间滚。**

量出来：画面上方那片**远墙与远树干整场一像素都不动**，跟着镜头动的只有它下面那一层
（中景树干、地面、前景一起平移，位移量完全相同）。所以那一层把镜头**加回来**，
抵掉世界那一趟的平移。它顺带解释了一件事：**录像里房间再宽，背景看起来也不"糊"。**

## 顺带量实的两条（不是改动，是确认）

- **高草挡人是对的**（上一片照录像改的那条）：那一帧里高草盖住他的裤腿和靴子，
  同一帧里木桶与高草也盖住两只哥布林的**下半身**。规矩就是**按落脚点排** ——
  和本作的贴地锚点排序是同一条。
- **它下面确实还有一档矮草**：40–90 像素高、一屏 8–16 丛、**从不遮人** ——
  那正是本作的「贴花」。

## 追记：业主说「怪物还是少」——量出来的答案不是"数量"

2026-10-13，三片点头之后他补了一句 **「我觉得怪物还是少」**。量的结果：

- **同屏数量本来就对得上**：录像 2–4 只（2–4 只占 32% 的帧），本作正房 3 只。
- **不对的是两件事**：**三只长得一模一样**，以及**一间房只有一组怪**。

**一、三只一模一样。** 客户端那一族本来就是**同一画布十具换色**（`goblin/body0..9`），
业主录像那块条上写过七个哥布林变体（哥布林 / 青哥布林 / 赤哥布林 / 胆小哥布林 /
投掷哥布林 / 燃烧之投掷哥布林 / 诅咒之赤哥布林），而本作原来只烘了 `body0` 一具青绿的。

颜色是**量的平均色**对上的：`body7` (44, 98, 129) 蓝 → **青哥布林**、
`body8` (145, 53, 45) 红 → **赤哥布林**。两具烘进来（图集从 6 行变 8 行、
文件 814 KB → 945 KB），走**同一个兵种**的数据，只是换张皮。

**二、一间房只有一组怪。** 录像里他在一间房待 17–45 秒，一路上遇到的是**几组** ——
那一群不围着他转（有的在他身前、有的在他身后），那正是"多组散布在房间里"的读法。
本作原来是**一组**，`x 620/790/880`。

所以每一间房现在是 **2 组**（正房 6 只，走道 4 只，Boss 房 门口一带 3 只 + Boss 一个）：
**同组贴着（相邻约 0.7 身位，59 像素），换组隔开两个身位以上（210–260）**。
§Q21 那条"聚成一团"的测试跟着改成**禁掉中间那个间距** —— 原来那个
`620/790/880` 正好落在"同组太远、换组太近"的缝里，那才是"一字排开"。

**"少"从来不是同屏不够密**：加同屏密度会把录像里那个"一两只在打"的节奏改掉，
而那是它读起来对的另一半。

## 追记二：02 套剩下那 19 件（客户端到手之后）

上一条的"摆密"只动了**数量**，手上还是那 14 件。客户端一到手就看清楚了：**02 套一共 33 件
道具**（另加覆雪孪生），我们只取了 14 件。补进来那 19 件是**真素材**——

- **贴地平铺的**（`grassPatch` / `leaves` / `leavesBroad` / `leavesDense` / `pebble`）：
  录像里满地就是这些，不是我们那三件轮着来。它们进 `SCENE.decals`，谁都不撞。
- **立着的**（三棵杉苗、两种倒木、四截断桩、两块暗色岩壁、两棵枯树）：
  进 `Core.SOLID`，盒子照老规矩量（**每件美术最底下 12 行的墨**）。

**立着的那批怎么撒**：它们挡人，而怪不会绕路（`docs/adr/0032`）。躲法不是"别撒"，
是**撒在带子深处** —— 本作的小怪站位最深到 depth 0.4，所以从 **0.55 往后**撒，
判定上就够不着（z 差 32 就相让）。

**踩到的一个坑值得记**：第一版撒出去的实心件**没有过「门口净空」那一关** ——
手写的那几件在 `beginRoom` 里会过（压门就挪、挪不开才丢），**撒的这批没走那条路**。
于是一根 223 像素宽的倒木正好横在一扇门前，人和演示 bot **都出不去**：
浏览器证明没红，`tests/attract.test.js` 那个
`while (!Attract.snapshot(session).victory && session.seconds < 60)` **转满一核六分钟**
（游戏时间不推进时它就是个死循环）。两处都修了：撒的实心件**跟手写的一个待遇**
（换几个位置再试、试不出来就丢），那条 `while` 也**加了帧上限**并在卡住时报错。

顺带清掉两条**烘了没人用**的死条目（`deathSmoke` / `deathBurst`，`docs/adr/0034` 之后
整条删掉的画法）—— 判据就是这条测试自己的话：「烘了没人用就是白烘」。

## 代价与未决

- **怪的种类还是 5 种**：录像那块条上写过 **7 个哥布林变体**（哥布林 / 胆小哥布林 /
  青哥布林 / 赤哥布林 / 投掷哥布林 / 燃烧之投掷哥布林 / 诅咒之赤哥布林），本作只有 3 个。
  **这一条卡在客户端**：换色要 `goblin/body1..9` 那几具烘进来，而这台机器上没有客户端
  （`docs/adr/0035` 的那条约束）。
- **Boss 房的布景没单独调**：量出来 R6 的地面是另一种砖、高草几乎为零（一屏 0–2 丛），
  本作现在六间房撒的是同一套。要分，改 `SCATTER` 就知道从哪儿下手。
- **实心件的密度还没补**：录像里石头是**一屏 2–7 块**（还成对、成 2–4 块的塌方堆），
  本作仍是一间房一两块。补它要先解决"怪被顶住"，不是加数据就行。
- **一屏几个数字分不出来**：量到的是"同时看得见多少"，整间房的件数是按屏宽折算的，
  好到大约 ±40%。
