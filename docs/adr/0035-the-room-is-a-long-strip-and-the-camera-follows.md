# 房间是一条横向长条，镜头跟着人滚

**Status**: accepted（2026-10-12）。业主在 grill 上答 **「Q11 选择 a」** ——
**推翻的是我给的推荐**（我推荐的是"不做、记进下一步候选"）。

## 决定

**一间房不再等于一屏，而是一条比屏幕宽的横向长条；镜头跟着他横向滚。**

在这之前 `ARENA` 是**定死的一屏**（960×540）：人走到 `x >= rightWall - 60` 就算从东门出去了，
所有门的 x 也按**这一屏的比例**量。这一条把那个前提换掉 ——
房间有自己的宽度，屏幕只是它的一个**窗口**。

## 为什么

**录像里就是这么跑的。** 在三个镜头真的在动的时刻量过：中景与地面**位移量相同**
（−32/−36、−18/−18、−29/−29、+22/+22 视频像素）—— 是一整块跟着人滚的平面，
**不是多层视差**，也不是"换一间房换一张画"。

业主这一轮的题面是「和参考视频相比，目前还有哪些区别」；房间会滚是量出来的差异之一，
而且是**尺寸**问题：不换这一条，"和录像一样"就有一条天花板。

## 被它推翻的

- **`ARENA` 是"一屏"这个前提**：宽从定值变成**每间房自己的**。
- **`docs/adr/0030` 里那些按屏幕比例量的门位**（上门 x = 0.673 / 0.492 / 0.469）：
  当时没区分"屏幕比例"与"房间比例"，现在必须选一个重述。
- **跑图 bot 与浏览器证明**：它们现在按"一屏之内走到墙边"过门。
- **「一间房几只怪」要重算**：现在的"正房 3 只 / 走道 2 只"是照**一屏**发的。

## 代价与未决

- **宽度、跟随律（有没有死区、有没有滞后）、边缘夹取、纵向跟不跟**：都还没量。
  按这一行的老规矩**先量再动手**，已经派出去量录像。
- **画幅**：录像的游戏画面是 **4:3**（1440×1080，左右是纯黑边），本作是 **16:9**（960×540）。
  加了镜头之后"一屏能看多宽"直接由它决定 —— 改不改画幅是**另一条决定**，没定之前不动。
- **场景道具要跟着铺满**：现在一间房 4–8 件，是按一屏摆的。
- **HUD 不跟着滚**：它在屏幕空间，这一条只动世界那一侧。

## 追记：量完之后，要动的其实是**远近**，不是房间宽度

业主给了整场录像（`dnf-dungeon-videos/00001-幽暗密林.mp4`，1920×1080，游戏画面居中
1440×1080）。六个房间、镜头逐帧跟下来，全部换成他**自己的一身位**（录像里 265 px、
本作 84 px）来比：

| | 录像 | 本作（改之前） |
| --- | --- | --- |
| 一屏高 | 1080 ÷ 265 = **4.0755 身位** | 540 ÷ 84 = **6.43 身位** |
| 一屏装多宽 | 1440 ÷ 265 = **5.43 身位** | 960 ÷ 84 = **11.43 身位** |
| 一间房多宽 | 3013 / 3519 / 3989 px = **11.4 / 13.3 / 15.1 身位** | **11.4 身位** |
| 他跑多快 | 330 px/s = **1.25 身位/s** | 159 px/s = **1.89 身位/s** |

**所以"把房间加宽"原本是一条走错的路**：本作的房间按身位算**本来就落在录像的最小那一档**
（11.4 对 11.4），一间房也不缺。录像的房间看着长，是因为**它的镜头紧** —— 一屏只装
5.43 身位，本作装 11.43。同一间房在录像里是 **2.1 屏**，在本作是 **1.0 屏**。

决定因此从"加宽房间"落成**"把世界画大"**：`CAMERA.zoom` = 132.51 ÷ 84 = **1.5775**
（一身位在录像里占屏高的 1/4.0755，本作一屏 540，于是 1 身位画 132.51 屏幕像素）。
一屏于是只看得到 **608.6 世界像素 = 7.245 身位**；**房间一个像素没动**，
却从 1.0 屏变成 **1.58 屏**，镜头自然有得滚。

**这也是业主那一轮说的「怪物少」的来源**：同屏 3 只的数量本来就对得上
（录像 2–4 只），但本作的窗口装着**两倍的世界**，同样三只摊在两倍面积上，看过去就稀了一半
—— 要补的不是怪，是**看得多近**。

镜头那三条也全是量的，逐条写在 `Core.CAMERA` 与 `updateCamera` 上：**死区**是屏宽的
**224/1440 = 15.556%**（居中，六个房间一致）、越过边界**一帧内到全速、跟他 1:1**
（30fps 下量不出任何滞后，所以代码里没有平滑）、**到墙就停**（他走到屏幕 x=1211
而镜头一动不动，连续 6.8 秒）、**纵向不跟**（95% 的帧 dy = 0）。
两个数由 `tests/core.test.js` 钉住：`zoom × 身位 == ARENA.height ÷ 4.0755`，
以及"死区边上才动、到墙就停"。

## 还差的三条（都没动）

- **画幅仍是 16:9，所以还差 33%**：拉近之后一屏 7.245 身位，录像的 4:3 是 5.434。
  业主 2026-10-12 定的是**先不动画幅**（Q16 选 a）—— 那 33% 单开一片。
- **速度差 1.5 倍**：按身位算本作的人跑得比录像快（1.89 对 1.25 身位/s），过一间房
  6.0 秒对录像的 9.1–12.1 秒。这一条**没动**。
- **房间宽度没动**：本作的房间（11.4 身位）仍比录像最宽的那一间（15.1）窄一档。
