## 2026-09-19 技能预览视频已破解

客户端每个技能都带一段官方预览视频（`Video/<职业>/<技能英文名>.avi`）。它外面套的是
「Neople Video File」容器，**不是真加密**：

- 前 32 字节是文件头（含明文长度），随后 **1024 字节明文**；
- 之后每个字节 = 明文自身 **异或 1024 字节前的明文**，所以可以从头迭代解出全文件；
- 解开后是普通 AVI（MPEG-1，160×90），可正常解码。

已用 `assets/decode_skill_videos.py` 把鬼剑士全部 **84 段**技能视频解密并导出到
`assets/dnf_src/skill-videos/`：每段一个 `.mp4`（可直接播放）+ 一张带帧号的
`<名字>.png` 全帧图 + `INDEX.txt`。

对照结论（与业主描述一致）：

- `HopSmash`（崩山击）：0-13 起手抬剑 → 14-27 前跃砸地、火焰冲击 → 28-49 蓝色冲击波
  → 50-57 收招。
- `GoreCross`（十字斩）：0-14 挥砍 → 17-33 十字成形并**向前推出** → 34-41 收招。

## 2026-09-20 特效包调色板与地面锚点（业主：「怒气爆发和崩山裂地斩的特效不对」）

复查结论：**包没选错，是烘焙方式错了**。客户端自己的预览视频把两个技能钉死了——
`BloodBlast`（怒气爆发）是原地插剑、脚下炸开血环、血柱从圈里升起；`OutRageBreak`（大蹦）是起跳、
砸地、裂缝张开、血气喷发。视频里的身体动作也正好对上这两招的行为（自身中心多段浮空 / 起跳砸地），
所以 `blastblood = 怒气爆发`、`outragebreak = 崩山裂地斩` 维持不变。

### 四个真正的原因

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| 大蹦「更乱」，看不出巨剑和裂缝 | `PICKS` 用通配符 `*` 拉整个包，而包里**同一套图形按色板存了三份**：无前缀（素色）、`(tn)`、`(18)`。崩山裂地斩烘了 **29 层**，其实只有 9 个形状，红 + 橙 + 橙叠在一起 | 一次只取一个色板；`*` 只展开当前色板；`_ldodge` / `_dodge` 这类同形状条目按名字点名 |
| 颜色也不对（业主第二次反馈） | 上一轮按「红色怒气圈」的文字描述保留了**素色（红）板**，而客户端实际播的是 `(tn)` 板 | 两行改取 `(tn)`（怒气爆发白金、大蹦橙火）；只有包里只存在素色版的 `blood_floor.img` 单独保留红色 |
| 两个特效都「不像那一招」 | 合成时短图层取模循环，6 帧的血环在 13 帧合成里重播两三次，合成帧是客户端从未出现过的一瞬间 | 所有图层按同一条时间轴取样（第 i 帧取各自的 `i/(n-1)`） |
| 怒气爆发的血柱飘在角色左上方，不在脚下 | 包内图层共用客户端坐标，**角色站在包自己的血环中心**，不是包围盒中心；居中摆放等于把整块特效平移了 | `PICKS` 声明 `anchor`（血环 / 裂缝的中心），烘图时锚点落在格子地面线（75%），渲染时该线对到角色脚下 |
| 大蹦没有「血气巨剑」 | `outragebreak_bloodsword_none.img` 原生只有 20×44，客户端靠技能动画数据放大，导出不带这份缩放 | 该图层按**落地中心**放大 5 倍再合成；其余图层保持原比例 |

### 十二、第三轮续八（2026-09-27，「还是有问题」）

这一轮查出一个**贯穿全招的量法错误**，它让前面几轮的「对齐」有一半是假的。

**列号映射错了。** 参考的帧号 → 渲染列号，正确的映射就是渲染器自己那一行：

```
progress = (n - 22) / 31        # 参考 32 帧摊在 1.07s 上
local    = progress / 0.97      # EFFECT.timing.crossSlash = {from 0, to 0.97}
col      = floor(local * 32)    # skillEffectFrame 里就是 floor
```

而我（以及 `fit2.py`）一直用 `round((n-22)/31/0.97*32)` —— **四舍五入，差一到两格**。

## 第二十六节 · 嗜魂封魔斩的第四轮：「高于手」是代码里多抬了一次（2026-10-05）

### 一、根因：深度抬升被减了两次（`src/render.js` 的 `drawBloodVortex`）

```js
ctx.translate(player.x, feetY(player) - Core.depthLift(player.z || 0));   // 旧
```
`feetY(body)` 自己就是 `body.y - Core.depthLift(body.z)`，所以整团漩涡比身体多抬
`z × DEPTH.scale`（0.22）px。实测（同一招、同一进度，只改 `DEPTH`）：

| | 漩涡近端墨迹离他脚 |
| --- | --- |
| z=0 | +0.65 … +1.00 身位 |
| z=400 | +1.70 … +2.04 身位 |
| 差 | **+1.048 身位 = depthLift(400)/84** |

业主截图里他站在带子中段（脚离地线约 34 canvas px，反推 z≈155），多抬 0.4 身位——
他看到的"高"就是这个。修法是一行：`ctx.translate(player.x, feetY(player))`。

**为什么前四轮量不出来**：`tests/browser/capture-effect.mjs` 的 `DEPTH` 默认 **0**，
而在 z=0 上两次抬升正好抵消，美术真的贴着手。四张对照图全是在默认深度拍的。
**规矩（这一节记的就是它）：一条挂在施法者身上的效果，证据图必须在 `DEPTH≠0` 再拍一张。**
对照图 `skill-clips/guifeng-hand-rootcause.png`（z=0 与 z=400 并排 + 深度 bug 的示意）。

### 七、业主实玩：「开始的时候在他上方出现，然后突然移到手附近」——一行效果的"单位"是客户端像素

这一条是业主实玩时看见的第二处 bug，量它只用了一张抓帧：进场那颗血球（`start-dodge`）的亮芯
在**身前 +1.13 / 离地 +1.35 身位**——他本人才 1.0 身位高，所以球是"在他头顶上"；
0.867s 之后**活画的漩涡**（它用的是本作px）出现在手边（身前 0.36 起）——中间那一跳就是这么来的。

**根因是单位，不是某一个数。** 这一行的 `size` 是照 `CELL / fit` 定的（烘焙自己打的
"`size` = 571 draws it 1:1"），也就是**1 客户端px = 1 屏幕px**；而本作的角色是客户端的
84/123.5 = **0.68 倍**。所以：

> **凡是"照参考量到的客户端坐标"，落进这一行之前都要 ×0.68 才是本作的屏幕px。**

进场三段（血球 / 铺开 / 收势）的 `offset` 当年正是照"客户端目标"解的——血球解到
客户端 (94, −108)（= 身前 0.76 / 离地 0.87 ✓ 与 §25 一致），但它被 1:1 地画了出来，
于是落在 (94, −108) 屏幕px = 身前 1.12 / 离地 1.29 —— **1.47 倍远**。
收尾那三段在 2026-10-05 重做时已经按 ×0.68 解过（见第五节），进场这三段是这次补的：

| 段 | 旧 offset | 新 offset | 新落点（身前/离地） |
| --- | --- | --- | --- |
| 血球 `start-dodge` | (24, −211) | **(−6, −177)** | 0.76 / 0.87 |
| 铺开 `line-dodge` | (88, −154) | **(40, −120)** | ≈1.20 / 0.85 |
| 收势 `casting_end_dodge` | (25, −206) | **(−5, −172)** | 0.76 / 0.87 |

**尺寸没有被这一次改到**：那几段的 `scale` 当年是按"画出来多大"试出来的，本来就接近
0.68 × 客户端尺度，所以只有落点错了——这也是为什么四轮对照图里"球的大小"一直是对的。
